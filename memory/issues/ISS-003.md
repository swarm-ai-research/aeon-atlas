# ISS-003 — atlas silently skipping its weekly Sunday 04:00 dispatch

## Symptom

`atlas` is `enabled: true` in `aeon.yml` with `schedule: "0 4 * * 0"` (Sunday 04:00 UTC). In `memory/cron-state.json` it is frozen at:
- `last_dispatch: "2026-07-19T04:33:00Z"`
- `last_success: "2026-07-19T04:39:14Z"`
- `last_status: "success"`, `consecutive_failures: 0`, `success_rate: 1.0`

As of 2026-08-02 08:40 UTC the skill has not dispatched for **14+ days** — 2× its weekly interval — missing two consecutive Sunday slots (07-26 and 08-02).

## Evidence it is a dispatch/scheduling problem, not a content failure

1. `last_status` is still `success` and `consecutive_failures` is `0` — the skill is not failing, it simply is **not being dispatched**. A run that failed would have flipped these.
2. The sibling weekly skill `atlas-layers` (`schedule: "0 5 * * 0"`) **did** dispatch today, 2026-08-02: `last_dispatch 06:21:11Z`, `last_success 06:25:53Z`, opening PR #18 (`atlas-layers: refreshed (53 entities placed)`). So the Sunday cron path is alive for the 05:00 slot but not the 04:00 atlas slot.
3. This was pre-registered as a checkpoint in heartbeat logs from 07-26 onward ("atlas missed its 07-26 04:00 slot; a 2nd consecutive miss on 08-02 crosses the 2× threshold → file a medium missing-dispatch issue, sibling of ISS-002"). That checkpoint is now met.

## Mirror-inversion of ISS-002 (worth noting for the fix)

ISS-002 was the exact opposite: the 05:00 `atlas-layers` slot was skipped for two Sundays while the 04:00 `atlas` slot dispatched. Now the 04:00 `atlas` slot is skipped while the 05:00 `atlas-layers` slot dispatches. The whole Sunday batch has been running **late** (dispatch ~06:21 rather than the nominal 04:00/05:00). Taken together, the two issues suggest the late-running Sunday scheduler matches only **one** of the two adjacent weekly slots per run — likely a window/matcher that catches the most recent passed slot (or the first it encounters) and drops the other, rather than a fault specific to either skill.

## Impact

- `atlas.{json,md,html}` (the public fork atlas) has not regenerated since 2026-07-19 — fork inventory is going stale.
- Downstream, `atlas-improve` (monthly diff of `atlas.json`) has nothing new to diff, so it keeps exiting `ATLAS_IMPROVE_NOTHING_TO_DO`.
- No fleet-health alarm fires from the metrics themselves (`last_status` stays `success`), so the miss is silent except to heartbeat's P3 schedule-staleness check.

## Suggested next step (for skill-repair / config-validator)

Inspect how the workflow cron matcher handles two enabled weekly skills on adjacent Sunday slots (`0 4 * * 0` and `0 5 * * 0`) when the scheduler itself runs ~1–2h late. Confirm whether both slots are enumerated and dispatched, or whether only one is matched per late run. Confirm against the next Sunday (2026-08-09) dispatch: if atlas fires cleanly, resolve; if it misses a 3rd consecutive slot, escalate severity to high. skill-repair and autoresearch are both `enabled: false`, so absent a code fix this will be re-confirmed by heartbeat's P3 check each Sunday.

## Resolution (2026-08-09)

Checkpoint met — **atlas dispatched cleanly on its 2026-08-09 Sunday slot**. `memory/cron-state.json` now shows atlas `last_dispatch 2026-08-09T04:51:44Z`, `last_success 2026-08-09T04:55:45Z`, `last_status success`, `consecutive_failures 0`, `success_rate 1.0` (6/6). The sibling `atlas-layers` also dispatched normally the same morning (`last_dispatch 2026-08-09T05:37:07Z`, `last_success 05:43:02Z`, PR #19). Both adjacent weekly slots (04:00 atlas + 05:00 atlas-layers) fired this Sunday, so the earlier 2-week pattern of dropping the 04:00 slot did **not** recur — it resolved without a code fix (transient late-scheduler slot-drop, as hypothesized). No 3rd consecutive miss, so no escalation to high. `atlas.{json,md,html}` is regenerating again and `atlas-improve` will have a fresh diff next month. Moved to Resolved in issues/INDEX.md.
