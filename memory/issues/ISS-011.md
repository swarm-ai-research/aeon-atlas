## Impact

- **~70.7h with no external-API health probe** — api-health-probe is the fleet's early-warning for dependency outages; a ~3-day gap means an upstream API degradation would surface as skill failures before the probe caught it.
- **~59.5h with no fork-first-run activation alerts** — new fork activations in this window go un-celebrated/un-logged until the next successful run (LRU seen-list means they're not lost, just delayed).

## Recommended durable fix (carried forward from ISS-005→009 — still operator-action-required)

The repeated lineage proves the per-slot self-heal loop is a reprieve, not a fix:
- **Redundant offset cron** — a second `schedule:` a few minutes offset from each slot so a single dropped cron delivery doesn't dark the slot.
- **External dispatch ping** — an off-GitHub scheduler (cron-job.org / external worker) calling `workflow_dispatch` as a backstop when native `schedule:` drops (also re-triggers hung runs).

`skill-repair` is still `enabled: false`, so no automated code fix will land — the backstop must be shipped by the operator.

Checkpoints: api-health-probe next due **10-31 10:00** (~1h from this run); fork-first-run-alert next due **10-31 20:30**; heartbeat **10-31 14:00 → 20:00**. Any fresh drop extends the window. Escalate to high if the self-check breaches 36h or the window goes full-day/multi-cadence.

The durable backstop should ship regardless of whether the skills self-recover — any auto-recovery is a reprieve, not a fix. Re-notify only on full resolution or a fresh P0 escalation (self-check breach / blackout).
