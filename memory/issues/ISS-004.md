# ISS-004 — heartbeat hung run + missed slots (2026-08-06)

## Symptom

As of the 2026-08-07 08:00 UTC heartbeat run, `memory/cron-state.json` shows:
- `last_dispatch: "2026-08-06T15:18:33Z"`
- `last_status: "dispatched"` (never advanced to `success`)
- `last_success: "2026-08-06T08:52:41Z"`
- `consecutive_failures: 0`, `success_rate: 0.84` (156/185)

By the stuck-skill rule (`last_status: "dispatched"` and `last_dispatch` > 45 min ago) heartbeat's own entry is **stuck** — the 08-06 14:00 slot was dispatched at 15:18:33Z and never completed. `memory/logs/2026-08-06.md` contains only the 08:00 slot entry; there is no 14:00 or 20:00 entry, confirming both later slots produced no output.

## Impact

- ~24h with no fleet health checks between the clean 08-06 08:00 run (last_success 08:52Z) and this 08-07 08:00 run.
- `docs/status.md` went stale (Updated 2026-08-06 08:51 UTC) for ~24h — past the ~8h staleness banner threshold.
- No data loss on other skills; the only enabled non-heartbeat skills are weekly/monthly (atlas*, next Sunday 08-09) and were not due in the gap window.

## Evidence it is a hung run, not a content failure

1. `last_status` is `dispatched`, not `failed`, and `consecutive_failures` is `0` — the run did not error out cleanly; it never reported back at all.
2. No log entry was written for the 14:00 or 20:00 slots — the process died before the log-write step, consistent with a hang/timeout rather than a handled failure.
3. This run (08-07 08:00) executed normally, so the skill has self-recovered; the condition is transient, not a standing outage.

## Note on lineage

This is distinct from resolved ISS-001 (recorder mis-classifying heartbeat *successes* as failed). Here the run genuinely did not complete — the `dispatched` state is accurate, not a mis-record. The `last_error` field still carries the harmless truncated-JSON usage fragment seen since ISS-001; it is not a real error signature.

## Suggested next step / checkpoint

Confirm against today's remaining slots: if the 2026-08-07 14:00 and 20:00 heartbeat runs dispatch and complete cleanly (log entries written, state advances to `success`), **resolve** this issue as a transient one-off hang. If another slot hangs (`dispatched` with no completion) within the next few cycles, escalate to **high** and investigate the workflow timeout / API-stall path for the heartbeat job. skill-repair is `enabled: false`, so absent a code fix this is re-confirmed by heartbeat's own P0 stuck check each cycle.

## Resolution (2026-08-07 20:09 UTC)

Checkpoint met. Both remaining 2026-08-07 slots dispatched and completed cleanly:
- **14:00 slot** — `last_dispatch 2026-08-07T14:17:42Z`, advanced to `last_status: success`, `last_success 2026-08-07T14:19:47Z`; log entry written (memory/logs/2026-08-07.md, 14:18 UTC).
- **20:00 slot** — this run, executing normally with a log entry written.

Three consecutive clean heartbeat runs (08-07 08:00, 14:00, 20:00) confirm the 08-06 hang was a **transient one-off**, not a standing outage. `consecutive_failures` remained `0` throughout; no other slot hung. No code fix was required. **Resolved as transient.** If a `dispatched`-with-no-completion recurs, re-open and escalate to high per the checkpoint above.
