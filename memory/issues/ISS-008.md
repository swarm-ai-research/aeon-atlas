# ISS-008 — scheduler quiet window, heartbeat missed the 2026-10-01 14:00 slot

## Symptom

As of this 2026-10-01 21:05 UTC heartbeat run (the 20:00 slot, ~1h5m late), `memory/cron-state.json` shows heartbeat at:
- `last_success: 2026-10-01T09:08:33Z`, `last_dispatch: 2026-10-01T09:06:33Z`, `last_status: success`, `consecutive_failures: 0`, `success_rate: 0.90` (271/300).
- Self-check: last_success is **~12h ago** (10-01 09:08 → 21:05), **under** the 36h P0 self-check threshold → self-check did **not** fire.

Slots this cycle:
- **10-01 08:00 — fired ~1h7m late** (ran 09:07, logged).
- **10-01 14:00 — MISSED** (no run, no state advance, no log; cron-state stayed frozen at the 09:08 success).
- **10-01 20:00 — dispatching ~1h5m late (this run, 21:05)** — scheduler alive again.

The 14:00 slot produced no run, no state advance, and no log entry. One missed slot, bracketed by two late-but-landed slots.

## Impact

- **~12h with no fleet health check** between the 08:00 catch-up run (last_success 09:08Z) and this 20:00 catch-up — one missing midday checkpoint.
- `docs/status.md` went stale (Updated 2026-10-01 09:07 UTC) for ~12h, modestly past the ~8h staleness banner but well short of a multi-slot blackout.
- No weekly/monthly atlas-cohort skill was due inside the window (atlas/atlas-layers next Sunday 10-04; atlas-improve's 10-01 06:00 monthly slot is tracked separately), so no atlas output was lost this cycle — but that also means this window offers **no cohort signal** to test whether the weakness is scheduler-wide vs heartbeat-cadence-specific.

## Distinction / lineage

Same signature as **ISS-005** (resolved 2026-09-05), **ISS-006** (resolved 2026-09-17), and **ISS-007** (resolved 2026-09-29): `last_status: success` with `last_dispatch` frozen — a **missed dispatch**, not a hung run (contrast ISS-004, which was `dispatched` and never reported back). ISS-005 established this as a **standing** GitHub Actions `schedule:` reliability problem (cron delivery is best-effort and drops under load / after inactivity).

ISS-007 was resolved only **2 days ago** on the basis of 3 consecutive clean slots (09-29 08:00 → 20:00), and 09-30 then delivered a full clean day-of-three. This 10-01 14:00 miss is therefore a **fresh recurrence** — filed as a **new** issue (not a reopen of ISS-007) per the ISS-005/006/007 closure convention that a fresh miss after resolution is a fresh signal. Severity **medium** (vs ISS-007's high) because it is a single isolated midday slot and the 36h self-check never tripped.

## Recommended durable fix (carried forward from ISS-005/006/007)

The repeated lineage argues the per-slot catch-up/self-resolve loop is not a fix. Options still outstanding:
- **Redundant offset cron** — add a second heartbeat schedule a few minutes offset from each slot so a single dropped cron delivery doesn't dark the whole slot.
- **External dispatch ping** — an off-GitHub scheduler (cron-job.org / external worker) calling `workflow_dispatch` as a backstop when the native `schedule:` drops.
