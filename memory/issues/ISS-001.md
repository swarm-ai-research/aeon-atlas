# ISS-001 — heartbeat recorded failed on every run despite executing

## Symptom

`memory/cron-state.json` shows heartbeat with:
- `total_runs: 29`, `total_successes: 0`, `total_failures: 29`
- `consecutive_failures: 29`, `success_rate: 0`
- `last_status: "failed"`, **no `last_success` field at all**
- `last_error: "7c38f12\",\"total_cost_usd\":0,\"usage\":{\"input_tokens\":0,\"cache_creation_input_tokens\":0,\"cache_read_input_tokens\":0,\"output_tokens\":0,...}"`

Yet heartbeat is clearly executing — this run produced output, regenerated `docs/status.md`, and earlier runs produced the prior status page template. A skill that never ran could not produce these artifacts.

## Evidence it is a recorder bug, not a content failure

1. The `last_error` is not an error message — it is a **tail fragment of a Claude Code result JSON** (`total_cost_usd`, `usage`, `server_tool_use`), with **all token counts zero**.
2. The **same signature** appears in `atlas-layers.last_error` (`"1e17804\",\"total_cost_usd\":0,...`), but atlas-layers still recorded `last_status: success` and a real `last_success`. So the fragment is captured on runs that the recorder otherwise treats as fine — the failure classification for heartbeat is the anomaly.
3. heartbeat has **zero** successes across 29 runs while continuing to be dispatched on schedule and produce files — a true 100%-failure skill would not be self-healing the status page.

## Impact

- Pollutes fleet health metrics: heartbeat shows 🔴 on its own status page.
- `consecutive_failures: 29` would trip the commented-out reactive `skill-repair` trigger (`consecutive_failures >= 3`) if enabled — false-positive repair churn.
- Masks any *real* heartbeat failure, since the signal is permanently saturated.

## Suggested next step (for skill-repair / autoresearch)

Inspect the cron state-update step in the workflow (the step that writes `last_status` / `last_error` from the Claude Code run result). Likely the success/failure branch keys off a field that is zero/empty on these runs (e.g. token usage or `is_error`) instead of the run's actual exit. Confirm against a heartbeat run that demonstrably succeeded, then correct the classification and reset heartbeat's counters.

## Resolution (2026-07-26)

Symptom cleared and has not recurred. As of 2026-07-26, `memory/cron-state.json` shows heartbeat with:
- `total_runs: 154`, `total_successes: 125`, `total_failures: 29`
- `consecutive_failures: 0`, `success_rate: 0.81`
- `last_status: "success"`, `last_success: "2026-07-25T20:17:48Z"` (field now present)
- `last_failed: "2026-06-06T12:56:45Z"` — the last recorded failure is the detection date itself

The recorder has classified **125 consecutive heartbeat runs as success since 2026-06-06** with zero additional failures. The misclassification that defined this issue (recording `failed` on every executing run) is no longer occurring — the state recorder now writes real successes for heartbeat and populated the previously-missing `last_success`. The 29 historical failures remain in the cumulative counters (they are frozen, all dated ≤ 2026-06-06); the residual all-zero-usage JSON fragment in `last_error` is stale detection-era data, not an active failure.

Closed by heartbeat rather than a repair skill because skill-repair/autoresearch are both `enabled: false`; no code-level root-cause fix was independently verified, so resolution is scoped to the **operational symptom** (125-run clean streak). If the zero-usage misclassification recurs, heartbeat's P0 check will re-file.
