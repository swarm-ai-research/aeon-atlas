# ISS-010 — api.semanticscholar.org keyless 429 (opened in error, closed wontfix)

## What happened

The 2026-10-27 11:00 UTC api-health-probe run probed all rows it found in the active registry table. `api.semanticscholar.org` returned **HTTP 429** (keyless rate-limit) on two consecutive probes and was absent from the prior `state.json`, so it initially looked like a notable first-ever DOWN and an issue was filed.

## Why it is not a real finding

Reading the full registry showed `api.semanticscholar.org` was **already in the "Excluded — needs a better probe" section** (added on the 2026-10-26 seed run): observed 429, reason "keyless requests are rate-limited", re-enable by probing with `x-api-key` (`SEMANTIC_SCHOLAR_API_KEY`). The excluded section exists precisely for hosts whose plain GET "does **not** return a liveness signal, so a probe would flag them DOWN even when the API is healthy." The keyless 429 is thus a known, documented, operator-acknowledged condition — not an outage and not a real transition.

The host was probed only because the seed run **also** left a duplicate row for it in the active table (both active and excluded). That duplication is the real defect.

## Resolution

- Removed the stale duplicate `api.semanticscholar.org` row from the registry's active table; the excluded-section entry (with the x-api-key re-enable instructions) remains the single source of truth.
- Dropped `api.semanticscholar.org` from `state.json` (excluded hosts are not tracked for transitions).
- No notification sent — the 25 genuinely-active hosts were all steady-state UP, so this run is a NOOP.
- Closed **wontfix**: the keyless 429 needs an `S2_API_KEY`/`SEMANTIC_SCHOLAR_API_KEY` header to probe clean, which is the operator action already captured in the excluded-section row. No new tracking issue is warranted.
